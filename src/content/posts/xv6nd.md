# xv6 Networking Lab: 从硬件到网络协议栈的穿透

## 1. 认知升级

以前写应用程序，思维惯性是“CPU 主动读写外设”。但在内核驱动开发中，核心哲学变成了\*\*“解耦与异步”\*\*。

### 1.1 MMIO 与 DMA：异步机制

控制 E1000 网卡用的是 **MMIO (内存映射 I/O)**。代码中 `regs[E1000_TDT] = ...` 看似在写普通内存，实则是把指令通过 PCIe 总线发给了网卡的物理引脚。

但真正解放 CPU 的是 **DMA (直接内存访问)**。发送数据包时，CPU 不需要把数据逐字节喂给网卡，而是把内存地址写进描述符，网卡自己会去内存里搬砖。 这就像老板（CPU）只需把任务清单（描述符）放在桌上，员工（网卡 DMA 引擎）自己拿清单去仓库（内存）取货。CPU 做最聪明的事（决定发什么），网卡做苦力（搬数据），这是高性能 I/O 的基石。

### 1.2 环形队列：软硬件的契约

驱动和网卡通信的桥梁是 **Ring Buffer（环形队列）**。它是一个固定大小的数组，通过 Head 和 Tail 指针实现循环。

```text
      硬件 (网卡 DMA)            软件 (内核驱动)
            |                         |
            v                         v
     Head (取货指针)            Tail (放货指针)
      |                         |
      v                         v
 [0] [1] [2] [3] [4] [5] [6] [7] ...
```

- **发送 (TX)**：内核驱动往 `Tail` 塞数据包地址，拨动 `Tail`；网卡看到 `Tail` 移动了，就从 `Head` 开始取包发送，发完拨动 `Head`。
- **契约位 (DD 位)**：如何判断某个槽位的包是否发完。描述符里有个 `DD (Descriptor Done)` 位。网卡发完自动置 1，内核看到 1 才能回收这块内存。这是软硬件之间最精妙的**无锁同步机制**。

## 2. 从零搭建：驱动与协议栈的代码实现

本次实验最大的工程量在于：不仅要写底层网卡驱动，还要写上层的 UDP 协议栈。2025 版的实验废弃了旧版的 `mbuf` 结构体，改用 `char *buf` 和 `kalloc`/`kfree` 直接管理物理内存，这要求对内存生命周期有极强的掌控力。

### 2.1 Part One: E1000 网卡驱动 (`kernel/e1000.c`)

**1.** `e1000_init()`**：硬件寄存器打地基**

- **做了什么**：配置网卡的 MMIO 寄存器，建立 TX/RX 环形队列的内存映射，并为接收队列预分配缓冲区。
- **怎么做**：
  1. **基地址与长度**：将全局数组 `tx_ring` 的物理地址写入 `E1000_TDBAL` 寄存器，将数组大小写入 `E1000_TDLEN`。
  2. **头尾清零**：将发送队列的头尾指针寄存器 `E1000_TDH` 和 `E1000_TDT` 置 0，表示队列初始为空。
  3. **接收队列的特殊处理**：对于 RX 队列，尾指针 `E1000_RDT` 必须初始化为 `RX_RING_SIZE - 1`。并且，必须用一个 `for` 循环遍历接收数组，为每一个描述符调用 `kalloc()` 分配一页物理内存，并将地址填入 `rx_ring[i].addr`，同时清空 `status`。
  - *思考*：如果不预先分配内存，网卡收到包时无处可写，就会直接把数据 DMA 到物理内存地址 0 处，瞬间摧毁内核代码。

**2.** `e1000_transmit(char *buf, int len)`**：发包与内存回收**

- **做了什么**：将上层传来的数据包地址填入发送描述符，并通知网卡发送，同时回收已发送完毕的旧包内存。
- **怎么做**：
  1. 获取 `tx_lock`，读取当前尾指针 `tdt = regs[E1000_TDT]`。
  2. 检查 `tx_ring[tdt].status` 的 `DD` 位。如果为 0，说明队列满了，释放锁并返回 `-1` 告知上层发送失败。
  3. 如果为 1，说明该槽位上的旧包已经发完了，立刻调用 `kfree(tx_buffers[tdt])` 释放旧包内存，并将 `tx_buffers[tdt] = 0` 清零防重入。
  4. 填充新描述符：`addr = (uint64)buf`，`length = len`，`cmd` 设置 `EOP`（包结束）和 `RS`（请求状态汇报），`status` 清 0。
  5. 将新的 `buf` 指针存入 `tx_buffers[tdt]` 以备将来释放。
  6. 推进尾指针：`regs[E1000_TDT] = (tdt + 1) % TX_RING_SIZE`，释放锁。

**3.** `e1000_recv()`**：中断驱动的收包机制**

- **做了什么**：在中断上下文中循环读取网卡收到的包，交给网络栈，并补充新的缓冲区。
- **怎么做**：
  1. 获取 `rx_lock`，进入 `while(1)` 循环（因为一次中断可能积攒了多个包）。
  2. 计算 `next = (regs[E1000_RDT] + 1) % RX_RING_SIZE`。
  3. 检查 `rx_ring[next].status & DD`。如果不为 1，说明没包了，`break` 跳出。
  4. 提取包指针和长度，调用 `net_rx(buf, len)` 交给上层。**注意：**`net_rx` **内部会决定是丢弃还是入队，如果丢弃它会自己** `kfree(buf)`**。**
  5. **关键动作**：立刻 `kalloc()` 分配新内存，赋值给 `rx_ring[next].addr`，并清空 `status = 0`。
  6. 推进尾指针 `regs[E1000_RDT] = next`，释放锁。
  - *思考*：如果不立刻补充新内存，网卡转一圈回来发现这个槽位还是旧的，就会直接把新包覆盖到旧内存里，导致数据错乱。

### 2.2 Part Two: UDP 协议栈 (`kernel/net.c`)

**1. 数据结构设计**

- 在 `net.c` 顶部定义了 `struct udp_recv_pcb`（保存源 IP、源端口、载荷长度、原始包指针 `pkt_buf`、载荷指针 `payload`）和 `struct udp_port`（包含绑定状态、自旋锁、16 个元素的 `pcb` 队列、头尾指针）。
- 为了避开 xv6 `free` 测试对物理页计数的严苛检查，放弃了 `kalloc` 动态分配，改用静态全局数组 `struct udp_port udp_ports[65536]`。

**2.** `ip_rx(char *buf, int len)`**：协议解析与生产者入队**

- **做了什么**：剥掉以太网和 IP 头，判断是 UDP 后，根据目的端口将载荷挂到对应端口的队列中。
- **怎么做**：
  1. 指针偏移：`struct ip *iphdr = (struct ip *)(buf + sizeof(struct eth))`。
  2. 协议判断：如果 `iphdr->ip_p == 17`（UDP）。
  3. 边界防御：如果 `len < sizeof(eth) + sizeof(ip) + sizeof(udp)`，说明是畸形包，直接 `kfree(buf)` 返回。
  4. 解析 UDP 头：提取 `dport = ntohs(udphdr->dport)`（必须转字节序）。
  5. 查找端口：如果端口已 `bind`，获取端口锁。检查队列是否满 `(tail+1)%16 != head`。
  6. 入队：计算真实载荷长度 `udp_total_len - sizeof(struct udp)`（绝不能用底层 `len` 减，因为可能有以太网填充）。把 `buf` 指针存入 `pcb->pkt_buf`，推进 `tail`，调用 `wakeup(up)` 唤醒消费者。
  7. **内存红线**：如果端口未绑定或队列满了，必须立刻 `kfree(buf)`，否则就是内存泄漏。

**3.** `sys_recv()`**：消费者取包与系统调用返回**

- **做了什么**：用户进程调用此函数，如果队列空则休眠；有包则取出，通过 `copyout` 拷贝到用户空间。
- **怎么做**：
  1. 用 `argint` 和 `argaddr` 获取 5 个系统调用参数。
  2. 获取端口锁，`while(head == tail)` 时调用 `sleep(up, &up->lock)` 休眠。
  3. 醒来后从 `queue[head]` 取包。
  4. **防御性编程**：检查 `maxlen < 0` 或 `payload_len < 0`，防止传给 `copyout` 后负数转 `uint64` 引发内存爆炸。
  5. 调用 `copyout` 将源 IP、源端口、载荷数据拷贝到用户态指针。
  6. 调用 `kfree(pcb->pkt_buf)` 释放内核缓冲区，推进 `head`，释放锁，返回载荷长度。

## 3. 网络协议的魔鬼细节：从物理层到 Socket

网络栈的解析过程中，数据包在内存里只是一串 `char *buf`，内核通过指针强转和偏移量逐层剥离头部。

### 3.1 字节序：大小端的世纪鸿沟

排查 `recv() failed` 时，我发现端口号对不上。网络传输规定多字节数据必须是大端序（高位字节在前），而 RISC-V/x86 CPU 是小端序（低位字节在前）。 如果收到包后不调用 `ntohs()` 转换，网络发来的 2000 端口（`0x07D0`），在 CPU 内存里会被读成 `0xD007`（53255）。这种 Bug 不会让系统崩溃，但会让数据无声无息地丢失。跨硬件通信，必须有一套统一的中间语言。

### 3.2 以太网填充与真实长度

测试报错 `wrong length 18, expecting 5`。这是因为以太网规定最小帧长 64 字节（不含 CRC）。如果发 5 字节载荷，网卡会自动补 0 填充到 60 字节。 我的 `ip_rx` 如果用底层的 `len` 去减头部长度，算出来就是 18，而不是真实的 5。 **破局点**：不能信底层传来的包长度，必须从 UDP 头部读取 `ulen` 字段来计算真实载荷长度。协议分层中“各层只信任自己的头部”的原则在此体现。

## 4. 并发：从死锁到细粒度锁

网络栈是高度并发的：多核 CPU 同时发包，同时网卡中断还在疯狂收包。锁的设计直接决定了系统的生死。

### 4.1 经典翻车：中断上下文中的自死锁

实验中卡在 `ping0` 一动不动，是一次典型的死锁事故。 当时我的逻辑是： 网卡收到 ARP 请求 -&gt; 触发中断 -&gt; `e1000_recv` 获取 `e1000_lock` -&gt; 交给上层处理 -&gt; 上层发现是 ARP，需要回复 -&gt; 调用 `e1000_transmit` -&gt; 试图再次获取 `e1000_lock`。 **CPU 拿着锁等自己释放锁，直接挂死。**

**破局思路：降低锁粒度。** TX（发送）和 RX（接收）是两个完全独立的环形队列，没理由用一把全局大锁。拆分为 `e1000_tx_lock` 和 `e1000_rx_lock` 后，收发通道彻底解耦，互不阻塞。

### 4.2 端口级锁：生产者与消费者的握手

在 UDP 协议栈层，`ip_rx`（生产者，中断上下文）往端口队列塞包，`sys_recv`（消费者，进程上下文）取包。 如果队列为空，进程不能死循环查，必须 `sleep`。这里体现了 OS 的经典睡/醒机制：

```c
// 消费者 (sys_recv)
acquire(&up->lock);
while(up->head == up->tail) {
    sleep(up, &up->lock); // 释放锁，休眠
}
// 取包...
release(&up->lock);

// 生产者
acquire(&up->lock);
// 入队...
wakeup(up); // 唤醒沉睡的消费者
release(&up->lock);
```

`sleep` 的精髓在于**原子性**：它必须在释放锁的同一步进入睡眠。否则一旦锁释放了、还没睡着时，网卡刚好塞了个包进来并调用 `wakeup`，这个唤醒信号就丢了，进程会永远睡死。

## 5. 系统级 Debug 方法论复盘

这次实验最大的收获不是写出了代码，而是建立了一套排查内核级 Bug 的思维框架。

### 5.1 工具武装：tcpdump 抓包定位

盲猜代码效率极低。当 QEMU 报错时，我使用了实验自带的抓包工具： `tcpdump -XXnr packets.pcap`通过查看真实的十六进制字节流，我能立刻判断出：到底是发送的包格式不对，还是压根没发出去。这是网络开发必备的“透视眼”。

### 5.2 现象 -&gt; 推理 -&gt; 定位

- **现象**：QEMU 疯狂刷屏 `Slirp: Failed to send packet`。
- **推理**：Slirp 是 QEMU 的用户态网络栈。它报错说明 xv6 发出来的包是乱码。为什么发乱码？因为接收端读到了内存里的垃圾数据，把它当成了 ARP 请求并尝试回复。
- **定位**：去查 `e1000_init` 的接收队列初始化。发现漏配了 `E1000_RDBAL`（接收队列基地址寄存器）。网卡不知道把收到的包写哪，直接写到了物理内存地址 0 处，把内核代码给覆盖了。
- **启示**：硬件驱动开发中，寄存器少配一个，就是核弹级灾难。报错现象往往在 A，但根因在 B。

### 5.3 边界与防御：不信任一切外部输入

跑 `free` 测试时报错 `lost too many free pages 32142`（丢了 3 万多页物理内存）。 这绝对不是普通的内存泄漏，而是**内存分配器链表被砸烂了**。 审计代码发现 `sys_recv` 里的 `copyout`：

```c
int copyout(pagetable_t pagetable, uint64 dstva, char *src, uint64 len)
```

如果用户态进程传进来的 `maxlen` 是负数，传给 `uint64 len` 会被强转成一个天文数字（2^64 - 1）。`copyout` 会疯狂往用户空间写，直接摧毁内核的物理页管理链表 `kmem.freelist`。 **启示**：内核态必须对一切来自用户态的参数抱有极度的偏执与不信任。防御性编程是操作系统的底线。

### 5.4 测试机制的弱点与工程妥协

解决完所有 Bug，最后还是差 36 页内存没归还。排查发现是 `sys_bind` 用 `kalloc` 给端口分配了内存，但 xv6 的 `sys_unbind` 是空函数，测试程序退出时没回收。 最后把动态分配改成了静态全局数组 `struct udp_port udp_ports[65536]`。因为静态数组在编译期就分配在 BSS 段，不占用 `kalloc` 的物理内存池，从而“骗”过了 `free` 测试。 **启示**：工程就是在约束条件下找最优解。了解测试机制（或者线上验收机制）的盲区，是快速交付的一种智慧。

## 6. 扩展视野：从 xv6 到工业界

做完 xv6 的网络栈，再去看真实世界的 Linux 内核和工业界网络方案。

### 6.1 Linux 的 NAPI 机制

xv6 中每收到一个包都会触发一次硬件中断，这在 xv6 的低流量下没问题。但在真实的高吞吐量服务器上，如果每秒进来上百万个小包，CPU 会瞬间被中断打爆，根本没时间去处理上层协议。

为了解决这个问题，Linux 引入了 **NAPI (New API)** 机制：

- **低流量时**：靠硬件中断唤醒内核来收包。
- **高流量时**：关闭硬件中断，内核主动采用**轮询**的方式去网卡里拉包。

这是一种极其精妙的动态反馈机制：既保证了低延迟，又防止了中断风暴。这正是运用了“批处理”的系统思维。

### 6.2 零拷贝与 DPDK

xv6 收包时，网卡 DMA 把数据写到内核内存，然后 `sys_recv` 再用 `copyout` 把数据从内核内存拷贝到用户进程的内存。 这次内存拷贝在千兆网卡时代无所谓，但在 100Gbps 的现代数据中心里，CPU 拷贝数据的速度根本赶不上网卡收发的速度。

工业界广泛使用 **DPDK (Data Plane Development Kit)** 或 Linux 的 `io_uring`/AF_XDP 技术： 跳过内核协议栈，网卡 DMA 直接把数据包写进用户态进程的内存里。这叫**零拷贝**。理解了 xv6 中出现过的BUG，才能深刻体会这些技术为什么是现代云计算底层的基石。

### 6.3 硬件卸载

E1000 描述符其实有很多高级字段（如硬件校验和卸载、TCP 分段卸载 TSO），但 xv6 统统没用，全靠 CPU 软件计算校验和。 现代高带宽网络下，这些计算极其消耗 CPU。真实驱动会配置这些硬件位，让网卡专用的 ASIC 芯片去算，这就是“硬件卸载”。操作系统的演进史，就是不断把 CPU 的脏活累活甩给专用硬件的历史。

## 结语

从硬件推导软件行为还是太难了。。。 回顾整个实验，其本质就是理顺一条从物理硬件到用户进程的完整数据链路。 当一个数据包抵达，它首先是一串电信号，被网卡通过 DMA 直接写进我们预分配的内核物理页里；紧接着硬件中断触发，e1000_recv 持锁接管，把这串无格式的字节流抛给上层；随后网络栈像剥洋葱一样，依次剥离以太网头、IP 头、UDP 头，将纯净的载荷塞进特定端口的环形队列，并唤醒沉睡的进程；最后，用户进程在 sys_recv 中醒来，通过 copyout 将数据搬到自己的用户空间，并 kfree 掉这块结束工作的内核内存。

在这条链路里，寄存器配置、环形队列、自旋锁、睡眠唤醒和虚拟内存拷贝精密咬合。任何一个环节的指针错位、锁粒度不当，或是边界校验缺失，都会引发连锁的内核崩溃或死锁。
